# 深度研究契约（可选模块）

这个模块解决的问题只有一个：**让「我当时的判断」变成可对账的资产，而不是一段会被反复改写的文字。**

它不负责产报告。产报告是你的活——可以自己写、可以让 Agent 写、可以接外部检索工具。这个模块负责：解析报告里的待验证命题 → 合并核对状态 → 挂进个股详情页。

---

## 一、为什么报告不可变、状态可变

想清楚这一条，后面所有格式约定都是自然的推论。

如果财报出来后你去改那篇报告，会得到两个后果：

1. **旧结论被抹掉**。半年后你看到一份「完全正确」的报告，会以为自己当时就判断对了。
2. **判断准确率无法审计**。而这恰恰是这套东西唯一真正值钱的地方——它不比任何研报更聪明，它只是能告诉你「你的判断力在过去两年是进步还是退步」。

所以：**报告是快照，状态是流水。** 两者都不许覆盖对方的职责。

要做第二版判断，就写新日期的新文件。`2026-03-15-research-hk00700.md` 和 `2026-01-08-research-hk00700.md` 并存，读的人自己对比。文件名里的日期就是版本号。

## 二、目录与命名

```
<实例根>/
  reports/
    2026-01/
      2026-01-08-research-hk00005.md     # 源文件，唯一真相
      2026-01-08-research-hk00005.html   # 渲染产物，给人看
  state/
    research-checks.json                 # 只存状态，不存正文
```

- 文件名格式 `YYYY-MM-DD-research-<主代码>.md`，必须与 `config/watchlist.yaml` 的主代码一致，否则脚本匹配不到。
- 详情页链接指向**同名同目录的 `.html`**。改了 `.md` 必须重新渲染出 `.html`，否则页面点进去是 404——脚本不检查这一层，因为怎么渲染由你决定。
- 同一标的多份报告时，**按文件名日期取最新**（`stem` 排序）。
- 删除 `reports/` 下的报告，详情页的对账卡自动变回「未覆盖」。这就是「可选模块」的开关，不需要改代码。
- `reports/` 属于私人产物，**必须被 `.gitignore` 排除**，不要提交进任何仓库。

## 三、报告格式契约

### 必需：一个一级标题

```markdown
# 标的名称：你到底想回答什么问题
```

标题会被抓取显示在详情页的入口条和卡片里。写成问题句最好——「补仓逻辑还在不在」比「2026 半年报分析」有用得多。

### 必需：`## 待验证命题` 小节

这是脚本唯一强制解析的结构。位置随意，但标题必须**逐字**包含「待验证命题」，且是二级标题。

表格四列，列名固定：

```markdown
## 待验证命题

| 编号 | 命题 | 核对指标 | 判定条件 |
|---|---|---|---|
| P1 | 净息差仍在收窄，但降幅收窄 | 单季净息差环比变动 | 环比降幅小于上一期则成立；走平或转正视为反转 |
| P2 | 存款定期化推高负债成本 | 定期存款占比与计息负债成本率 | 定期占比继续上升且成本率不降则成立 |
```

写这三列时有硬要求：

| 列 | 要求 | 不合格的样子 |
|---|---|---|
| 命题 | 一句可判真假的陈述句，不含程度副词 | 「基本面承压」——不可判 |
| 核对指标 | **必须是你自己的财报快照里查得到的字段** | 「市场情绪」——查不到 |
| 判定条件 | 写清在什么数值下成立、什么数值下反转 | 「看情况」——没法核 |

**挂不上指标的命题不要写。** 这是整件事的闸门：它把「观点」强制翻译成「待验证命题」。挂不上说明这条判断本身没落地，那条知乎回答/那段访谈再精彩也只是情绪。

建议 3–5 条。少于 3 条通常说明研究没做透，多于 5 条通常是在凑数——读者不会认真核第 6 条。

### 可选：其余小节

自由写。正文里值得保留的是三类东西：

- **机制解释**：为什么这个数字会这样动，而不是「这个数字很差」
- **反例与边界**：在什么条件下结论会反转
- **你自己不做什么**：不给目标价、不外推行业、不预测利率路径——写清楚能防住大部分误用

报告里**不要给买卖点**。研究归研究，区间归区间，两个体系混在一起会互相污染。

## 四、状态文件 `state/research-checks.json`

```json
{
  "source": "manual",
  "as_of": "2026-11-13",
  "checks": {
    "hk00005": {
      "research": "2026-01-08-research-hk00005",
      "researched_at": "2026-01-08",
      "source_label": "知乎深度研究",
      "next_check": "2026Q3 季报 · 按上年同期推断约 2026-11 下旬",
      "items": [
        {"id": "P1", "status": "partial", "verified_at": "2026-01-20",
         "verified_period": "2026Q2", "evidence": "降幅收窄成立、走平未成立"}
      ]
    }
  }
}
```

| 字段 | 说明 |
|---|---|
| `status` | `pending` 待观察 / `confirmed` 已证实 / `refuted` 已证伪 / `partial` 部分成立 |
| `evidence` | 一句话写清凭什么这么判。空着不算核对过 |
| `source_label` | 入口显示的来源名，缺省「深度研究」。**不要写死在代码里**：这个包不假定你的研究来自哪 |
| `next_check` | 下次核对的时点。按上年同期披露日推断时，**要写「推断」二字** |

规则：

- 只有这一次核对改了状态，才更新 `verified_at`。
- 报告正文与这里冲突时，**以报告为准**——`items` 里只有状态，没有命题正文。这是刻意设计：避免两份真相。
- 状态文件由人或授权会话「先读后写」，构建脚本**只读**。

## 五、详情页上长什么样

三个落点，缺一个都不成立：

1. **顶栏按钮** —— 独立样式，不要复用「返回」按钮的类。同款样式会让内容入口退化成导航。
2. **首屏入口条** —— 挂在「一句话结论」卡内，显示报告标题 + 命题条数。对账卡位置靠后，只靠顶栏按钮触达率不够。
3. **页内对账卡** —— 命题 + 核对指标 + 判定条件 + 状态徽章 + 信源分工 + 下次核对。

**信源分工那一行不能省。** 如果只标「某社区深度研究」，读的人会以为毛利率这类硬数字也出自社区——而它们其实来自你自己的财报快照。标错来源比不标更糟。

## 六、研究从哪来

包不管这事，但给几条实测过的路径。

### 知乎（推荐用于「真问题」，不推荐用于日常个股体感）

知乎开放平台提供了 CLI 与配套 Skill，能力包括站内搜索、全网搜索、问题推荐、回答列表、知识库。它能拿到的东西是**观点与过来人叙述**，不是数据。

**实测结论（2026-11，60 条抽样）：**

| 话题类型 | 检索质量 | 说明 |
|---|---|---|
| 技术选型、消费决策、职业体验 | 好 | 能出高赞真人长文，有具体细节 |
| 一级市场、行业规则、估值方法论 | 较好 | 有律所专文、从业者分析 |
| **个股经营体感**（产能、压库、渠道政策） | **差** | 用经营术语检索，40 条里 37 条是自媒体专栏文章，赞同数 0–6，发布时间跨 2019–2026，部分为洗稿且数字造假 |

所以用法上有一条硬边界：**拿它回答「这类东西该怎么看」，不要拿它回答「这家公司上季度怎么样」。**

调用时三个已知限制：

- 搜索接口不返回可靠的发布时间，**必须自己标「时效未知」**，不要默认是最近的
- 回答列表接口只给截断摘要 + 链接，不返回赞同数/作者/时间，无法做质量筛选
- 所有调用消耗账号额度，且额度按自然日计算

用之前先想清楚一个问题：这份报告要验证的是**机制**还是**当期数字**？如果是后者，你的财报快照比任何社区都准。

### 其他来源

行业访谈、年报与招股书原文、你自己长期跟踪的笔记、上游供应商公开信息。只要最后能落成「待验证命题」，来源是什么不重要。

## 七、常见错误

1. **把报告当文档改**。财报后直接编辑原报告 → 半年后无法回溯判断准确率。写新文件。
2. **命题挂不上指标**。写成「品牌力下滑」这种不可判的陈述，对账时只能凭感觉。
3. **状态全是待观察就以为模块没生效**。这是正常状态，第一次财报出来后才会动。
4. **在 `reports/` 里放真实持仓明细**。那是私人数据，`reports/` 会被提交进仓库的话就泄露了。持仓只在 `config/`。
5. **报告里给目标价**。会和 `config/buy-bands.yaml` 的区间体系打架，两套口径互相污染。
